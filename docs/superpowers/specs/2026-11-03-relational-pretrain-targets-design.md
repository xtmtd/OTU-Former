# Relational Pretraining Targets Design

**Status:** Revised draft for user approval after source-level audit. No implementation, training, commit, push, or release is authorized by this document.

**Baseline:** `main` at `f959d3b` (package version `0.11.2`, preflight consistency already implemented). This identifies the implementation baseline, not an assertion that a tag or release has been published. Proposed implementation target: `0.12.0`, subject to approval; do not change version files during this design revision. Two things are breaking: the new-run recipe changes, and the CLI loses `--disable-cross-view-loss`. This is not a major-version requirement.

**Revision record:** this draft was revised through several source-level audit rounds. The change log is kept by topic in the appendix rather than by external finding identifiers, which a reader cannot resolve here.

**Superseded (branch `OTU-Former-dense`):** v2's data path and its DINO CLS
method were rebased onto `0.12.0`, so two claims below no longer hold. Marked
v2/DINO payloads are no longer rejected as cross-branch: the SSL method is what
a resume may not change, and same-method v2 payloads resume normally
(`resolve_pretrain_ssl_config`). The "no new SSL method" non-goal applied to the
`0.12.0` branch only; `--ssl-method dino` now exists and is mutually exclusive
with the relational targets described here. Everything else in this document
still describes the shipped relational recipe.

## Intent

Improve the reliability and cross-view consistency of the existing batch-relative relational CLS objective on the current `main` branch. The change is motivated by small-data experiments and ReSSL literature, but does not claim established gains for OTU delineation.

## Goals

- Start every new run with a strict student-to-teacher encoder state copy, preserving the student's existing initialization and restoring resumed pairs without synchronizing them.
- Give the relational teacher a weak global view by default for new runs.
- Compute the relational CLS loss using cross-view pairs only: student view A against teacher view B, and student view B against teacher view A.
- Resolve omitted temperature endpoints to effective new-run defaults `0.08` and `0.11`; their declared CLI/request defaults are `None`, so omission can inherit on resume.
- Preserve historical main checkpoint resume behavior and downstream checkpoint compatibility; reject a cross-method resume before output mutation (a marked payload of the same method resumes normally — see the superseded note above).
- Keep the weak teacher transform and its resolved settings traceable in logs/checkpoints.

## Non-goals

- No FIFO relation queue, queue-size option, or queued features.
- No Adaptive Similarity Bootstrapping (AdaSim).
- No new SSL method or command on the `0.12.0` branch, and no import of v2's DINO prototype mode there. Main already has the batch-relative relational `_ssl_loss`; adapt it in place. (The v2 rebase later added `--ssl-method dino` as a separate, mutually exclusive method.)
- No initialization selector, independent-initialization fresh-run compatibility mode, backbone-source change, or DINO-style projector reinitialization. A cross-method pretrain resume is unsupported; same-method resumes stay supported, including DINO payloads after the v2 rebase. Read-only/downstream checkpoint consumers are not restricted by this training-only boundary.
- Weak views do not supply patch teacher inputs, patch tokens, or patch centers. This is a control-variable choice, not a patch-loss result established by ReSSL.
- Do not claim all patch targets are unchanged: the shared teacher temperature change affects `ibot_patch_loss` sharpening. `consistency` and `masked-feature` do not consume this temperature. Shared-backbone training can change all branches indirectly.
- Keep the batch candidate set, self-similarity entries, relational softmax formula, and existing center update formula. Center input population is an explicit ablation choice as specified below. No separate local/patch temperature, diagonal masking, or loss-weight retuning.
- No claim that weak augmentation improves dense morphology or OTU quality without controlled evaluation.

## Approaches Considered

1. **Adapt the existing relational path (chosen).** Add same-weight fresh-run initialization, weak relational teacher views, cross-view-only pairing, and the requested temperature defaults to the existing pretraining path. This reuses the current relational loss, dataset, and checkpoint structure and keeps the change attributable.
2. **Introduce a separate ReSSL mode or replace the global objective with a new loss.** Rejected because the current code already implements batch-relative relational SSL; a new mode would duplicate the objective and expand configuration/resume complexity without being required for this change.
3. **Add queue and AdaSim together with the view changes.** Deferred to future v2 development and validation. These introduce stale-feature, cache-quality, and schedule interactions that are outside the current `main` scope.

## Confirmed Behavior

### Same-weight initialization for new runs

The operator selected fixed same-weight initialization for all fresh runs, with no CLI selector. Keep the student's existing construction, pretrained backbone source, projector initializer, register migration, and zero center. Do not turn this into from-scratch backbone training or adopt v2 DINO's truncated-normal projector initialization. After constructing both encoders with matching architecture and before the first diagnostic or training forward, execute `teacher.load_state_dict(student.state_dict(), strict=True)` under `no_grad`, then keep every teacher parameter frozen. Copy parameters and buffers, including the projector, center, added/native registers, their positional entries, and any registered aliases. Do not share tensor storage or model objects. Construct the teacher independently rather than deep-copying the model; preserve the existing teacher-construction RNG handling rather than changing the seeded stream as a second experiment. The fresh-run full-state copy replaces the register-only synchronization call in `run_pretrain`; inspect the helper's callers before removing it. Existing independent iBOT head construction and its student-to-teacher state copy remain unchanged.

On every resume, including historical full/same recipes, restore the saved student, teacher, centers, patch objective, optimizer, progress and RNG through the existing paths; do not copy student state over the teacher, reset a center, or replay initialization. No initialization key is added to the seven-key target bundle: initialization is a fixed fresh-run rule, not a resumable target selector. A re-saved legacy run must not be described as having started with synchronized encoders merely because the saving executable uses the new fresh-run rule. Document the fresh/resume branch and retain the existing invocation/version provenance rather than fabricating historical initialization metadata.

This aligns the initial EMA pair with common DINO/ReSSL practice and removes an independently initialized teacher projector as an early source of mismatch; it does not establish improved stability or OTU quality. Equal weights do not promise equal outputs across different views, teacher centering, or stochastic forwards. The startup ordinary-A cosine keeps its existing formula and is not required to equal one. All six fresh-run comparison arms below use this same initialization; none measures its effect against the historical independent-projector initialization.

### Weak relational teacher views

For a new run, generate two independent weak global teacher views by default. Teacher CLS features from these views supply both global-to-global and local-to-global relational losses. They do not supply patch-loss targets. Student global/local views remain the existing views; patch teacher inputs remain the corresponding ordinary global views. Weak A/B identify the two teacher slots, not geometrically registered copies of student A/B. Do not claim same-position patch correspondence between independently sampled weak and ordinary crops.

The v3 paper does report ReSSL experiments with ViT-Small and ViT-Base. It still describes ReSSL as an image-level relational method; separately, it characterizes masked-image-modeling patch prediction as a distinct objective and future complementary direction. The official ReSSL release code (`ressl.py`, `ressl_multi.py`) computes image-level query/key logits against a queue and has no patch/token loss. However, its released backbone registry contains ResNet-18/34/50 only, so that code is not direct implementation evidence for the reported ViT experiments. Together, the paper and code support the qualified conclusion that weak teacher views are used for ReSSL's image-level relational targets, not patch supervision in the described/released ReSSL method. They do **not** provide a controlled comparison of applying weak views to an iBOT/MIM patch objective. Keeping this project's patch input path separate is therefore consistent with ReSSL's stated objective and isolates variables, but it is not proof that weak augmentation cannot benefit patch learning. Removing strong teacher photometric corruption remains a reliability hypothesis to test, not a guaranteed OTU improvement.

The weak transform is a separate resolved transform derived from the existing pretraining augmentation configuration:

- Mirror the **resolved `augmentation_config`**, not a second interpretation of CLI policy: global crop size/scale, aspect ratio, rotation degrees/interpolation/expand/fill, post-rotation resize/order, horizontal and vertical flip probabilities, and tensor conversion. Ordinary normalization currently comes from the transform's ImageNet constants, not config keys: add the exact weak-record mapping `normalize: {mean: [0.485, 0.456, 0.406], std: [0.229, 0.224, 0.225]}`. The canonical paths are `weak_teacher_augmentation_config.normalize.mean` and `.normalize.std`; both are ordered length-three lists of finite, non-boolean numbers, with strictly positive std entries. The builder copies the effective ordinary constants into fresh lists; `_build_pretrain_view_transform` passes these recorded values to `normalize_mean`/`normalize_std` for weak globals and rejects a missing/malformed normalize record rather than silently falling back. Ordinary transforms keep their existing constant defaults. Compare weak normalization to the executed ordinary transform, not to a nonexistent ordinary config field. Do not mutate or add normalization keys to the historical ordinary config.
- Keep the existing global crop scale `[0.4, 1.0]`. ReSSL's `[0.2, 1.0]` is not independently validated for diagnostic insect morphology; the decision to retain 0.4 is a project adaptation, not a proven optimum.
- For `global-barcode` and `color-robust`, `sensitive` means rotation `[-15, 15]` with no reflection; `invariant` means rotation `[-180, 180]`, horizontal flip probability 0.5, and no vertical reflection. Preserve the resolved edge-median fill and expanded rotation/resize behavior.
- **`legacy` is the exception:** it ignores `orientation-policy` for transforms. Mirror its resolved broad rotation, horizontal/vertical flips (0.5 each), fixed black fill, unexpanded rotation, and absence of post-rotation resize. Do not silently apply the modern sensitive geometry to legacy.
- Disable color jitter (probability and amplitudes zero), grayscale, and Gaussian blur in both weak global views. Preserve ImageNet tensor normalization; normalization is not augmentation strength, but it is part of the executed transform, so the weak record must carry the effective normalization parameters rather than inheriting them silently from a module constant.
- `solarization_probability` has no consumer in the transform code; keep it at its existing inert `0.0` and do not add an execution path for it.
- The weak record is locked as a whole and is an execution contract first: only the fields a weak global view actually consumes affect pixels (global crop size/scale, crop ratio, rotation parameters, flips, post-rotation resize, fill, tensor conversion, normalization). Fields the deep copy drags along that no weak global view consumes (`local_crop`, `local_crops`, `blur.local_kernel`, `blur.probabilities[2]`) take no part in the weak forward, but they still take part in the checkpoint consistency check: the record is locked as a whole, so a change confined to them is still drift. No field whitelist is added; if that strictness proves wrong in practice, define an explicit exclusion set instead of silently ignoring the fields. The recorded normalization is binding in the stronger sense as well: the weak transform must build its `Normalize` from the record rather than from a module constant, so the recorded value actually controls pixels. Two locks are deliberately redundant and cheap to keep: the weak record's geometry fields duplicate what the ordinary-config check already covers, and the recorded normalization can only diverge through a hand-edited config. Keep both; removing either is a simplification, not a fix.
- Student/global, local, and patch-teacher views continue using the unmodified selected profile. Neither `color-robust` nor `legacy` may re-enable weak-teacher photometric operations.

Expose one value-taking option, `--relational-teacher-views {weak,ordinary}`. `weak` generates the two independent weak teacher globals for relational targets; `ordinary` reuses the existing ordinary globals and generates no extra weak crops. Omitted is an internal `None` request, resolved to `weak` for a new run or inherited on resume; `None` is not a public choice. Do not expose positive/negative boolean aliases. Track explicit values even when they equal the effective new-run default.

Keep the separate ablation option `--relational-center-source {weak,ordinary}`: it selects which teacher CLS features update the existing running center, not which losses are paired. Its omitted request is resolved to the teacher-view source on a new run or inherited on resume. An ordinary teacher-view source allows only an ordinary center; weak teacher views allow either center source. This option exists to separate the target-source effect from the center-population effect, not as a replacement for the old pairing flag. No per-transform parameter bundle is added. Help, schema, logs, and bilingual docs distinguish omitted requests from effective settings.

### Three independent controls

| Option | What it selects | What it does not select |
| --- | --- | --- |
| `--relational-teacher-views weak/ordinary` | Teacher images used to construct relational target features. | Global loss pair selection or patch teacher images. |
| `--relational-center-source weak/ordinary` | Teacher feature population used to update the running CLS center for subsequent steps. The current pre-step center is subtracted before L2 normalization. | Which A/B loss pairs contribute. |
| `--relational-pairing cross/full` | Global student/teacher view-index pairs averaged in the loss. | Image augmentation source or center population. |

For global pairs, `cross` averages A-to-B and B-to-A; `full` averages A-to-A, A-to-B, B-to-A, and B-to-B. Historical `--disable-cross-view-loss=true` selected only A-to-A and B-to-B (`same`), while false selected `full`. Thus the old flag controls pairing, not centering, and is replaced by `--relational-pairing`, **not** by `--relational-center-source`. Historical `same` is therefore reachable only through legacy checkpoint metadata on resume; it is not a `--relational-pairing` choice and has no new-run CLI spelling. Local-to-global pairing is unchanged.

Example: `--relational-teacher-views weak --relational-center-source ordinary --relational-pairing cross` constructs relational targets from weak images, updates the center from ordinary teacher features, and averages only the two cross-index global losses. Normal new runs can omit all three options and resolve to weak views, weak center, and cross pairing.

### Dataset and batch interface

Keep the existing flat list and default PyTorch collation; do not introduce a new batch object. With `L=local_crops`:

- Weak views disabled: `[global_A, global_B, local_0, ..., local_(L-1)]`, length `2 + L` (the historical contract).
- Weak views enabled: append `[weak_teacher_A, weak_teacher_B]` **after all ordinary local views**, length `4 + L`.
- Read ordinary globals as `views[:2]`, locals as `views[2:2+L]`, and weak globals as `views[2+L:4+L]` only when enabled. Never use unbounded `views[2:]` with weak views enabled. Reject unexpected counts/shapes rather than treating weak globals as locals.
- Default collation yields one `(B, 3, H, W)` tensor per list slot, with the existing global/local sizes. Validate weak slots using distinct `weak_teacher_A`/`weak_teacher_B` names.
- Preserve direct `MultiCropDataset` callers by making its internal `include_weak_teacher_views` boolean argument default false. That constructor default is for existing direct dataset callers; `run_pretrain` must not rely on it. At the dataset callsite, `run_pretrain` must take `relational_teacher_views` from the resolved recipe and reject `None` or any value outside `weak`/`ordinary` before deriving `include_weak_teacher_views`. Do not compare the raw CLI request to `weak`: an omitted request would silently disable weak crops. Pass the derived boolean directly to the dataset without adding it to `args` or the checkpoint recipe. The public/saved setting remains the `relational_teacher_views` enum. This prevents accidental reuse of the reserved experimental metadata name `weak_relational_teacher_views`; the current saver serializes `vars(args)` except the `_UNSAVED_ARGS` handoffs (`resume_state` and `pretrain_settings`), so local implementation details must not be attached to that Namespace. Update callers/tests that assert view count rather than silently changing their default contract.
- Add keyword-only `augmentation_config: dict[str, object] | None = None` and `weak_teacher_augmentation_config: dict[str, object] | None = None` beside `include_weak_teacher_views: bool = False`. A supplied ordinary config is the transform source of truth; validate its profile, orientation, global/local sizes and local count against the existing constructor arguments and reject mismatches before building transforms rather than silently choosing a winner. The trainer passes effective profile/policy/sizes/count and the exact preflight-validated configs; the dataset does not rebuild supplied configs. Direct callers without an ordinary config retain the historical builder. With weak views enabled, use a supplied weak config as the pixel source after checking mirrored geometry and disabled photometric operations against the effective ordinary config; otherwise derive it once. Its explicit normalization may differ for direct config-driven tests, but trainer/resume requires the exact resolved record. Reject non-null weak config when weak views are disabled. Do not mutate supplied configs. Cover conflicting profile/policy/size/count, compatible non-default recorded normalization, no rebuilding of supplied configs, and historical no-config calls in tests.
- Generate ordinary views first, then weak views. Keep the existing `_estimate_edge_fill` calculation over ordinary transforms: weak geometry mirrors ordinary, so it adds no new fill mode; test the unchanged edge-median/fixed-black behavior with weak views enabled. Initial diagnostic `sample_batch[:2]` remains an ordinary-global diagnostic and must be labeled as such, not as a weak-target measurement.

### Teacher forward and center contract

Use one EMA teacher model and its existing CLS center; do not add heads, a second encoder, or a second CLS center. For step `k`:

1. Snapshot the pre-step CLS center `c_k`. The selected relational teacher inputs are the two weak globals when enabled, otherwise the two ordinary globals.
2. Produce the two selected relational features using the historical formula `t_v = normalize(teacher_cls(v) - c_k)`. Under `no_grad`, use these same features as teacher anchors/candidates for global and local relational losses.
3. Update the CLS center **once** using the configured `relational_center_source`: `c_(k+1) = 0.9*c_k + 0.1*mean(concat(t_A,t_B))`, where `t_A/t_B` are computed from that center source using the pre-step center. Preserve the historical centered-and-normalized update population, not raw projector outputs. `weak` selects weak features; `ordinary` selects both ordinary-global features. Never combine both populations or update once per forward. With weak views disabled only `ordinary` is valid.
4. When a patch objective is active and weak views are enabled, separately forward the two ordinary globals for patch targets. Keep same-position geometry, patch tokens/final-four layers, and iBOT teacher logits/patch-center updates on that ordinary path. These forwards do not update the relational CLS center. With weak disabled, reuse ordinary forwards; with `patch-loss=none`, skip patch-only forwards.
5. Build targets before the existing optimizer/teacher EMA update, and update teacher parameters once per optimization step. Do not update teacher EMA for each weak/ordinary view. The existing independent patch-center update remains independent.

With weak views enabled, run both weak teacher globals. Also run both ordinary teacher globals when a patch objective or the ordinary center source requires them; otherwise run ordinary global A for the preserved cosine diagnostic. Reuse ordinary outputs rather than forwarding them again for each consumer. This adds two teacher forwards relative to historical main when both ordinary globals are needed, or one when only ordinary A is needed. It adds no trainable parameters. The default recipe is the expensive case: `--patch-loss consistency` is the default, so a new run performs four teacher forwards per step instead of two and two extra augmentation crops per sample. State the training-time and activation-memory impact in the README and the release note. Tests must compare fixed ordinary patch inputs, masks, and teacher state to establish input-path isolation; changed RNG consumption, shared training updates, or stochastic backbone behavior mean whole training trajectories and patch losses are not promised to be bitwise identical.

### Diagnostic metric continuity

Preserve `cosine_similarity` as the cosine between the batch-mean student CLS projection for ordinary global A and the batch-mean `normalize(teacher_cls(ordinary_A) - c_k)`, using cached pre-optimizer teacher features and the pre-step center exactly as in historical main. Weak target/center selection must not replace the teacher side with weak-A features. Reuse ordinary patch/center forwards, or obtain ordinary-A specifically when neither needs it; that diagnostic forward never updates the CLS center or teacher EMA. Preserve this definition in the instant-metrics table the code already writes (`logs/instant_metrics.pretrain.csv`), the `COS` progress-bar field, and the curves built from it; this is **not** `logs/metrics.pretrain.csv`, which is the periodic embedding evaluation and must stay unchanged (no added epoch column, no migrated header). Document its ordinary-A input source rather than silently reusing the column for strong-versus-weak similarity. Initial `sample_batch[:2]` diagnostics remain ordinary-view diagnostics. Changing the center recipe may change numeric values, but not the metric's input-view definition.

### Cross-view-only relational loss

New runs default to `cross`: average student A-to-teacher B and student B-to-teacher A. Local-to-global pairing still averages every local student crop against both selected relational teacher globals. Only the global pairing policy changes.

Expose `--relational-pairing {cross,full}` (omitted request `None`, effective new-run value `cross`), so a fresh baseline can explicitly request `full`. Remove `--disable-cross-view-loss` from the CLI entirely rather than keeping it as an alias. It carries no remaining meaning: its only reachable value is a single switch whose `true` meant the historical `same` pairing, an explicit `false` was never typeable (`typer.Option(False, "--disable-cross-view-loss")` has no `--no-...` spelling), and `same` is now published nowhere as a new-run recipe. Do not use a current invocation's missing/leftover boolean or a synthetic CLI `False` default to resolve a fresh request as `full`. `run_pretrain` rejects any invocation Namespace containing `disable_cross_view_loss`, by key presence even when false or null, before dataset/model construction or trainer-owned output mutation; the error names removed `--disable-cross-view-loss` and replacement `--relational-pairing`. Do not silently ignore direct callers' stale requests. This gate applies to invocation args, not the separately loaded checkpoint's historical `args`: a saved checkpoint boolean `False` means `full`; an absent historical field also assumes `False`/`full`, with the named warning required below. `--relational-pairing` is the sole pairing control: `cross` (new-run default) and `full`. Deleting the option leaves the CLI's own unknown-option error; the release note and the command reference must name the replacement, and no hidden compatibility shim is added. Keep internal `same` pairing solely to resume legacy checkpoints that recorded `disable_cross_view_loss=true`; it is not reachable from a new run at all, and never through `--relational-pairing`. All policies average over the pairs actually selected. `_compute_global_loss` receives exactly two student-global and two selected teacher-global features, never the full dataset view list. Validate those counts; internal `same` is valid only with ordinary teacher views and uses `(0,0)`/`(1,1)`. Weak slots are separated at batch unpacking, not extra elements to zip into global pair selection. Schema/skill display may report inherited `same` as an effective checkpoint value, but must not add `same` to `--relational-pairing`'s choices or reject a valid legacy resume merely because the public choices are cross/full. The pure cross selector replaces the old boolean rather than adding a new SSL mode. This revised selector is proposed for approval because the previous draft could not express its own baseline.

The candidate axis is unchanged: `teacher_out @ teacher_out.T` includes same-image diagonal self-similarity, which remains in both cross-view pairs. For non-degenerate, unit-L2-normalized teacher features, the unshifted diagonal is exactly `1 / teacher_temp` up to floating-point arithmetic. This qualification does not assert unit norm for a zero/epsilon-clamped normalization input or change the existing normalization formula. Subtracting each row's mean leaves its softmax unchanged; it does not suppress diagonal mass. View-pair exclusion is **not** diagonal masking, and raising temperature does not itself change L2 normalization. Report target diagonal probability/entropy rather than describing unit norm as a temperature effect.

The hypothesis is that excluding same-index global view pairs removes an easy consistency route and emphasizes cross-view prediction; neither this code nor the cited small-data experiments proves that same-index terms are always harmful or provides a universal DINO-style justification. Even same-index slots use independently augmented inputs when weak views are enabled.

Historically `L_global_full=(L_AA+L_AB+L_BA+L_BB)/4`; the new default is `L_global_cross=(L_AB+L_BA)/2`. Each retained term's coefficient changes from 1/4 to 1/2, **but the global mean's coefficient in total loss remains 1**. `lambda_local` and `lambda_mask` remain unchanged. Global loss/gradient magnitude may change with the selected terms, but it is not automatically doubled relative to local/patch loss. Log and evaluate the component losses; do not add a compensating scale by assumption.

### Teacher temperatures

Declare `--teacher-temp-start/end` as optional floats defaulting to `None`; resolve fresh omissions to `0.08/0.11` and resumed omissions from checkpoint metadata. Help and schema distinguish declared/request defaults (`null`) from effective fresh defaults and resume inheritance. `Parameters:` records null for omitted endpoints; do not replace it with effective values for display. Keep the linear-ramp-then-plateau shape, but take the ramp fraction from `--teacher-temp-warmup-ratio` instead of the hardcoded `0.7`. The option is added by this change: a float in the **closed** range `[0, 1]` with declared/request default `0.7` and effective fresh default `0.7`, applied as `int(total_steps * ratio)` exactly as the current constant is applied, so the default is bit-identical to today's schedule. `ratio=0` means no ramp at all (the end temperature from step zero) and `ratio=1` allocates every planned step to the ramp with no plateau; both are legal. Preserve `np.linspace(start, end, warmup_iters, dtype=np.float32)`: when `warmup_iters=1`, that one ramp value is **start**, not end, including a one-step plan at ratio 1. When truncation gives zero ramp steps, use end throughout. Do not change this arithmetic to make a smoke run reach end. It is a schedule field, not a relational recipe field: it is written to `args`, inherited on resume, and deliberately **not** part of the seven-key bundle. Unlike the five optional recipe fields, an omitted ratio remains `0.7` in requested `Parameters:` even when resume resolves it to `0.3`; this is a request record, not an effective schedule claim. Track `teacher_temp_warmup_ratio_explicit` and print the inherited `0.3` in `Teacher temperature schedule:`; saved `args` carries effective `0.3`. Test both logs and provenance for this exact case rather than requiring six null request fields. Retain this request interface deliberately: on an omitted-ratio resume proposal, schema `values["teacher_temp_warmup_ratio"]` remains declared request `0.7`, provenance is `omitted-inherited`, and unresolved guidance must state that the effective ratio requires checkpoint validation; never present that merged request value as the inherited effective value. An explicit `0.7` stays explicit and conflicts at runtime with saved `0.3`. Saved `args.teacher_temp_warmup_ratio` is its authoritative location in this main-only format: validate a present value as a non-boolean finite number in `[0, 1]`, inherit it, and re-save it unchanged. A checkpoint that does not record it is treated as the historical `0.7`, that assumption is warned about, and an explicit non-default ratio against such a checkpoint is rejected rather than silently applied. Present null, bool, nonfinite or out-of-range saved values fail instead of falling back. Use exact normalized numeric request matching as for the endpoints.

Two different limits apply here and must not be conflated. **Numerical validation** bounds temperature scaling of finite, normalized `float32` teacher features; it is not a promise that the whole loss is finite. Reject booleans, nonfinite/nonpositive endpoints, and values that become zero or nonfinite at schedule `float32` precision. For a normalized cosine row, each scaled entry has magnitude at most approximately `1/tau`, and subtracting its mean can produce magnitude up to approximately `2/tau`. Stable softmax subtracts a row maximum internally, but cannot repair an infinity/NaN already produced by the preceding division, `mean` or subtraction.

The current `teacher_sim.mean(dim=1)` may overflow in an intermediate reduction before division by row length. `B/tau` is a **conservative worst-case absolute-sum bound**, not the actual row sum or mean for every feature batch; the actual sum depends on similarities and the reduction kernel. Preserve one deterministic guard for both that reduction and centered span. Let `f = np.finfo(np.float32)`, `tau32 = float(np.float32(tau))`, `limit = float(f.max) * (1.0 - 4.0 * float(f.eps))`, and `bound = float(max(B, 2)) / tau32`, with limit/bound computed in Python binary64 after the tau cast. Admit exactly when tau32 is positive finite, bound is finite, and `bound <= limit`; equality is admitted. This fixed four-epsilon reserve is the chosen guard margin, not a proof of all backend arithmetic or a tunable option. Do not use an alternative float32 division path with different boundary rounding. Here `_ssl_loss` receives one view's `(B,D)` features, its relation matrix is `(B,B)`, and `B=args.batch_size` on every executed step because the loader drops the last incomplete batch. If the dataset has fewer samples than batch_size, the loader is empty and the existing startup `next(iter(loader))` fails; this admission guard does not promise a nonempty loader, and empty-loader behavior is not changed here. Additional views/pairs do not increase row length. A finite Python double quotient alone is insufficient: the explicit comparison to the reserved float32 maximum is mandatory. Retain requested endpoint values, not their rounded copies, in metadata and explicit-request comparisons.

Make the regression input explicit: repeated **identical unit vectors** give a row of `1/tau`. On the inspected PyTorch 2.12.1 CPU path, `tau=2e-38` yields finite mean/loss/backward at `B=6` and an infinite mean/NaN loss at `B=7`, whereas random normalized features can remain finite at both batches. At `B=6, tau=6e-39`, even `2/tau` is finite but the identical-vector reduction overflows; a batch-independent `2/tau` check is therefore insufficient for this unchanged implementation. Test the conservative guard itself deterministically, use these fixed vectors to verify the mechanism on the validation CPU backend, and record the backend/version; do not require all backends or arbitrary random inputs to overflow identically. The guard intentionally rejects values outside the worst-case bound even if one observed batch happens to be finite. Keep separate format legality (positive finite value remains positive finite in `float32`) and conservative run admission (the bound for this run's batch and centered span). Re-evaluate admission when resuming at a different batch size. This is neither an exact failure threshold nor a new batch cap; changing the reduction algorithm to admit more extreme temperatures is out of scope. The `--patch-loss ibot` path divides unnormalized prototype logits by the same temperature, so the unit-cosine argument does not bound it; record that dependence instead of claiming coverage. Values such as `0.0009` stay format-legal and are inherited, subject to the per-run batch check. **New-run policy band `0.001..100`** applies only to fresh requests: it is project policy about plannable signal and no part of the numerical safety argument. The band is policy, not a claimed optimum, and it does not change the schedule algorithm. Do not justify it as a guarantee that the target keeps useful spread: at the lower edge the target is already saturated (`32` orthogonal unit vectors at `0.001` give diagonal probability `1.0` and zero off-diagonal mass), so the band is a default-policy convenience, not a signal guarantee. The upper bound is deliberately generous: at the top of the band the target is already nearly uniform (`exp(2/100)` ~ `1.02` for the worst-case unit-vector spread), so the band must not be presented as proof that the target still carries usable signal. Non-finite values and booleans are rejected explicitly: `True` is not `1.0`. A rejected endpoint is a CLI parameter error raised before any output mutation.

Compatibility of saved values: an endpoint that is numerically safe but outside the policy band — a `0.0009` written by an older run, for example — is inherited from the checkpoint, re-saved unchanged, and re-inherited on the next hop; an explicit request equal to that effective saved value is accepted. Rejecting such a value would be an intentional breaking compatibility change, not a numerical fix, and is not proposed here. Explicit matching uses a different type rule from the config tree: reject booleans first, then normalize any accepted numeric to `float` and compare by value, so an explicit `--teacher-temp-start 1` legitimately matches a saved integer `1`. Compare normalized floats with exact numeric equality, not an absolute tolerance: saved `2e-20` and requested `2e-13` differ by a factor of ten million but would pass `abs_tol=1e-12`. The strict type rule below applies to bundle and config-tree comparison, not to numeric request matching. These are the existing **shared** teacher temperatures, not a new DINO or separate relational-only schedule:

| Consumer | Effect of changing the teacher schedule |
| --- | --- |
| Global relational `_compute_global_loss` / `_ssl_loss` | Changes teacher relation probabilities. |
| Local-to-global relational `_compute_local_loss` / `_ssl_loss` | Changes teacher relation probabilities whenever locals are used. |
| `--patch-loss ibot` / `ibot_patch_loss` | Changes prototype target sharpening on ordinary patch inputs. |
| `--patch-loss consistency` or `masked-feature` | No direct temperature dependency; input path/formula is unchanged. |

Keep student temperature, loss weights, schedule arithmetic, and patch-center logic unchanged. A 'temperature-only' ablation means changing this one **shared schedule**, not isolating global relations from local/iBOT effects. For a separate global-only diagnostic use `--local-crops 0 --patch-loss none` for both control and treatment; that diagnostic is a different protocol, not evidence of unchanged behavior in the full objective.

### Checkpoint and resume compatibility

Current main rebuilds teacher schedules from invocation `args`; it does **not** already inherit/validate these temperatures. The implementation must add a resolver, not merely change CLI defaults.

**Canonical location:** every checkpoint saved by the updated code, including a legacy resume, writes the following complete bundle to `config.relational_target_config`:

- `version: 1`;
- `relational_teacher_views: weak | ordinary`;
- `relational_pairing: cross | full | same`; (`same` is serialized only when carrying a legacy recipe forward.) `weak` teacher views combined with `same` is contradictory and rejected even when every field is present, because `same` describes a historical ordinary-view payload only.
- `teacher_temp_start`, `teacher_temp_end`: numerically safe numbers (see Teacher temperatures), never booleans; the new-run policy band is not reapplied to preserved values;
- `relational_center_source: weak | ordinary`, using the same key in CLI/args and this bundle; `relational_teacher_views=ordinary` requires an ordinary center, while weak teacher views allow either center source;
- `weak_teacher_augmentation_config`: the fully resolved two-global weak transform, including the effective normalization parameters, or `null` when disabled; a change to the recorded normalization is drift and must fail resume.

This bundle is authoritative. Also write the resolved teacher-view enum, pairing, center source, and temperature endpoints into saved `args` for provenance, but never reconstruct future behavior from the removed CLI boolean. For `relational_teacher_views`, `relational_pairing`, `relational_center_source`, and both temperature endpoints, compare the same-named bundle and saved-args fields and reject conflicting duplicate values rather than choosing whichever is convenient. Equality here is **type-strict**, not plain `==`: validate each side's type first, then compare recursively keeping `bool`, `int`, `float`, and `str` distinct so `true` never equals `1` and `false` never equals `0.0`, with lists compared in order. Plain Python comparison would accept a corruption the bundle rules require rejecting. The earlier draft spelling `teacher_center_source` is not an alias: do not emit or silently read it in a version-1 bundle. A bundle missing `relational_center_source` fails as incomplete; an old-spelling field alongside it fails as ambiguous. No released checkpoint-format migration is needed for this unimplemented draft rename. Preserve the encoder/projector tensor layout, existing center state, and all unchanged checkpoint fields; downstream loaders must tolerate the additive config bundle. This is not a new tensor format. Compatibility is **one-directional**: updated code may resume older checkpoints, but an older trainer reading a new checkpoint ignores this bundle and therefore does not restore the weak/cross recipe; accepting the file is not evidence that the recipe was preserved. A related consequence belongs to the preflight work: isolating the `auto` size lookup and the model probes under `preserved_rng` stops them consuming the seeded stream, so a given `--seed` no longer reproduces `0.11.1` student initialization. Historical `teacher_temp_start/end` and `disable_cross_view_loss` are not new-style markers. A reachable example starts with 5 epochs × 10 steps (50 steps), requests extension to a **total of 10 epochs** at completed epoch count 2/global step 20, then saves an interrupted extension at completed epoch count 3/global step 30 (`epoch=2` in the zero-based payload). ## Research Evidence Boundary

ReSSL (NeurIPS 2021, arXiv `2107.09282`) and Weak Augmentation Guided Relational Self-Supervised Learning v3 (arXiv `2203.08717v3`) motivate weak image-level relational targets. The latter reports ViT-S/ViT-B results, but the inspected official release repository does not contain that ViT implementation: its released backbone registry is ResNet-only. Its paper describes ReSSL as global/image-level relational learning and positions masked patch prediction as a distinct MIM direction; released ReSSL training code has no patch loss. This supports, but does not experimentally isolate against, a project's iBOT/MIM patch objective. Neither source validates this main branch's patch behavior, independently validates the 0.4 crop floor, or proves global/local/iBOT effects are isolated. Project run logs showing a weak flag do not establish the exact dirty transform implementation. Cite them for the ReSSL mechanism and the limited image-level scope, not as evidence that patch learning is unaffected.

Initialization precedent: official [DINO](https://github.com/facebookresearch/dino/blob/main/main_dino.py), [DINOv2](https://github.com/facebookresearch/dinov2/blob/main/dinov2/train/ssl_meta_arch.py), and [ReSSL](https://github.com/mingkai-zheng/ReSSL/blob/main/network/ressl.py) synchronize the initial student/query state into the teacher/key encoder. This is evidence of the convention, not an OTU efficacy result or a claim to reproduce their complete recipes.

## Extension note — 2026-11-11

This design's **no-queue** boundary remains the default and is unchanged: a
relational run with capacity zero takes the batch-only loss, data path and
reporting it describes here. The later [relational FIFO design](2026-11-10-relational-fifo-design.md)
adds an opt-in, explicitly enabled extension — `--relational-queue-size` with a
positive capacity — that keeps the current batch candidates and appends recent
teacher observations. Where that feature is enabled it also adds an enabled-only
input identity contract, strict epoch recovery and extra instant-metric columns;
none of those apply to a disabled run, and this document is not rewritten.
