## 1. Intent and constraints

Make `otuformer pretrain` and `otuformer finetune` cheaper to run and easier to test without making the rest of OTU-Former depend on the trainers. Reduce demonstrated repeated work in `extract`, `cluster`, `annotate`, `diversity`, `cam`, and `export` while preserving the products their consumers depend on. Optimize single-run CPU and accelerator execution before considering parallel or distributed redesigns. The [master design](2026-03-29-otuformer-design.md), [training modularity design](2026-11-07-training-modularity-cli-testing-design.md), and [development testing policy](2026-11-07-development-testing-policy.md) remain authoritative. The in-tree pretrain startup handoff (`_PretrainHandoff`, `resume_payload_for`, `_UNLOADED`) is the established precedent for path-bound payload reuse; finetune should follow its proven behavior, not copy an unbound payload parameter. The local v2 roadmap (`ref/otuformer-v2-development-roadmap.md`) motivates narrow reusable data and feature contracts, not a second general-purpose training framework. The [Coordinate/Ranking design](2026-11-15-otuformer-coordinate-ranking-consistency-design.md) governs its objectives and recovery; its equivalence tests are not current production timing evidence.

Preserve existing CLI defaults and flags, the `training.trainer` import-and-call entry points, checkpoint and CSV schemas, and the semantics of the exported embeddings. No new generic trainer, public task or head API, downstream example task, fast-mode flag, dependency, or accelerator policy. Do not change any objective formula, mask or sampling policy, batch size, pair weighting, temperature, teacher/center/FIFO update order, or checkpoint layout. Intentional behavior differences are sampled evaluation's decode boundary and the per-invocation manifest snapshot, including one nonfatal startup warning instead of retrying a failed manifest at each save (§3 and E1), the correction of cluster's monophyly metric to use the fixed output tree (§6.2), and earlier rejection of deterministic embedding-export preflight errors (§6.6). Semantic equivalence does not mean promising bitwise equality across differently shaped kernels or backends.

## 2. Approaches and selection

| Approach | Trade-off |
| --- | --- |
| A and B only: trim periodic evaluation and centralize finetune preparation | Fixes observable evaluation and startup duplication but leaves known repeated step work untouched. |
| Training only: A and B plus focused hot-path candidates | Addresses training costs, but misses documented duplicate work and failure boundaries in downstream commands. |
| **One workflow design with independently accepted changes (selected for design)** | Adds only traced downstream changes. Each performance candidate is optional if it changes a contract, adds complexity, or does not pay off. Consumer-chain tests are shared, not runners or generic configuration. |
| Unify the loops or change the execution backend first | Broader batching, compilation, and mixed precision may help, but introduce unrelated memory, numerical, RNG, and resume questions. A generic loop does not remove any identified repeated calculation on its own. |

The design is one document with independent acceptance units: A (evaluation), B (finetune preparation), C1–C7 (training step candidates), D1–D6 (downstream), and E1–E6 (architecture/preflight decisions with explicit dispositions in §7). No change depends on a new shared runner or on approval of all the others.

## 3. A — Select evaluation rows before image decoding and forward

**Current path.** The CLI default for `--metrics-sample-size` is 10,000 in both pretrain and finetune; the user documentation agrees, and all 24 available local run logs record 10,000. At each eligible save epoch, `training/reporting.py` rereads the evaluation CSV, resolves paths, opens images serially, and runs raw backbone CLS for every row before applying the cap to features and labels. Thus a manifest larger than the effective cap is still fully decoded and forwarded before sampling (for example, 20,000 rows with the default cap decodes and forwards all 20,000); selection-before-decode can avoid work only when the cap is active. For manifests at or below the cap, sampling changes nothing. The 230-row `examples/Epidorcus/figs.csv` (230 image files) is such a case: potential savings there are repeated CSV reading and path resolution, including recursive image-index construction when bare filenames cannot resolve directly, not skipped image decodes or forwards. Evaluation failures warn and skip that epoch's metrics. `num_workers` does not parallelize this evaluator.

**Proposed behavior.** If embedding metrics are enabled and an evaluation CSV is configured (`visualize_data` or `train_data`), prepare it once at training startup under E1. Preserve `pretrain_loop._compute_and_log_all_metrics`, `reporting._compute_embeddings_from_csv`, and `reporting._maybe_subsample_for_metrics` with their current module-level names and old calling forms; if an optional prepared-manifest argument is added, preserve direct legacy calls. The known direct-call and monkeypatch contracts are in `test_pretrain_alignment.py` (four `_compute_and_log_all_metrics` calls at 392, 460, 505, 553; `_compute_embeddings_from_csv` call/patch at 343, 369, 439, 484, 526; `_maybe_subsample_for_metrics` direct/patch at 411, 533, 1852). If E4 sampling ownership changes one of these symbols, keep a compatibility wrapper or update all listed nodes in the same task. Use the existing lookup rules and require every resolved path to be an existing file before sampling; an unresolved fallback cannot be hidden by sampling. Freeze the ordered rows, resolved paths and labels together. Do not deduplicate or reorder rows. Apply the same seeded, sorted selection without replacement to paths and labels before decoding, using the same sorted-index semantics as the current implementation. Task 9 later extracts the shared index rule in E4 after parity checks. Nonpositive caps or caps at least as large as the manifest still evaluate every row.

**Accepted boundary.** An unusable manifest emits one startup warning and skips periodic embedding evaluation for this invocation without stopping training. This is not the same as `--disable-embedding-metrics`: retain the epoch metrics logger (and its header-only CSV if no epoch succeeds) and pass its path to the training-curves plot as today. The explicit disable flag continues to omit the epoch logger and bypasses evaluation-manifest parsing and path checks entirely; independent training and output-safety validation still runs. Mid-run CSV edits or repairs do not take effect until the next invocation, including resume. After successful preparation, sampled files are still opened at evaluation time; decode failures warn and skip that epoch's metrics, while unsampled corrupt or removed files are not checked again. No images are cached and evaluation remains serial. Keep raw CLS, preprocessing, image size, conditions for supervised metrics and plots, and both linear-probe schedules. Keep teacher evaluation in `pretrain` before the checkpoint RNG snapshot and model evaluation in `finetune` after saving.

**Acceptance.** Compare selected rows and labels (including duplicates, unlabeled and single-class inputs), raw CLS features, numerical metrics and plot inputs with the full-forward-then-select reference. Count manifest preparation at every path use, including loader-step prediction, overwrite protection and A evaluation, plus image decodes and forwarded rows for capped, uncapped and disabled evaluation. For shared training/evaluation manifests, assert the implementation really resolves one selection and reuses its exact identity-checked paths; retain separate resolution only where selected populations or validation contracts differ. Performance acceptance must include a matched manifest larger than the effective cap (the default is 10,000), or explicitly lower the cap for that measurement; otherwise decode/forward savings are necessarily zero and cannot validate this part of A. Make avoided decode/forward rows, path-resolution calls and recursive-index (`rglob`) walks the primary expected-work evidence; use paired wall time as secondary evidence, especially for small manifests such as the 230-row repository example. If no representative over-cap workload or cap override is available, record the limitation and leave this benefit unqualified rather than closing A as no-benefit from an undersized workload. Cover a missing or malformed CSV, an unresolved, ambiguous or non-file entry outside the sample, one warning with training and checkpointing continuing, and no retry after the CSV is repaired. Confirm valid CSV row/path/label edits do not change the live snapshot but are picked up on the next invocation. Cover sampled versus unsampled corrupt or removed files, private state per E1, both save boundaries, and unchanged training RNG streams. Measure the evaluation phase separately from training.

## 4. B — Prepare finetune decisions once, before output mutation

**Current path.** `cli/finetune.py` reads resume metadata for inheritance and then reads the same checkpoint again for source preflight. It already forwards the validated payload to `run_finetune`; the runner, however, separately resolves the loss and repeats parts of the source and lineage validation. New pseudo rounds also read a source for inheritance and hand off to an existing pseudo preparation routine. The pseudo-source checkpoint and the SSL checkpoint used to initialize a new round are distinct roles, not duplicate loads to elide by name.

**Proposed ownership.** Put shared startup decisions in one training-side preparation entry, using existing `finetune_support.py` owners where possible. CLI keeps parsing, help, explicit-option provenance, progress/error presentation, output protection, and overwrite confirmation. It asks for preparation before clearing or creating outputs and passes the prepared result to execution. Direct use of `run_finetune` still works and invokes the same preparation when it has no prepared result, including when given a preloaded payload through the existing call interface. Keep the handoff private; do not put it into saved args. Preparation may read inputs and, when requested, perform the existing in-memory pseudo round. It must not create or clear outputs. Do not move data/model/optimizer-dependent checks merely to make a promise that *all* startup failures precede writes.

| Source mode | Preparation invariant |
| --- | --- |
| New run from `--checkpoint` | The loaded initialization payload drives source classification, effective loss and source-layout/lineage decisions. Keep the existing distinction between fresh SSL initialization and initialization from a metric checkpoint, including head selection. |
| `--resume` (ordinary or pseudo) | Read one resume payload for inheritance, explicit conflict checks, and subsequent restore. Preserve legacy fallback and recorded effective identity. A pseudo resume uses its saved accepted rows and lineage, does not regenerate candidates or require the original SSL file, and still checks an explicitly supplied pseudo-source hash when the current contract requires it. |
| New pseudo round | Inherit only according to the existing pseudo-round rules; use the same pseudo-source state for those decisions and its preparation where both need the payload. Keep the separate SSL initialization payload and its lineage/hash checks. Preserve real class-row order, manifest checks, rejection of ineligible or empty rounds, and the rule that no pseudo artifacts are written before setup succeeds at the existing boundary. |

Mirror the pretrain handoff invariant: a payload may be reused only for the invocation path it was loaded from; if the requested path changes, reload it. Keep decision/configuration state in the private handoff rather than conflating requested, explicitly supplied, inherited, and effective options. In particular, an inherited pseudo-round loss parameter must remain effective without being mistaken for a conflicting user override. Retain model-name precedence, payload format acceptance/rejection, warnings for allowed resume drift, and source-file hashing/protection. Reusing a deserialized payload does not remove an independent file-integrity check. The runner retains dataset/class checks, model and optimizer construction and state restoration, and training updates; it consumes the resolved source/loss decisions rather than re-resolving them. Avoid changing the shared read-only checkpoint resolver or giving `finetune` read-only consumers' head-selection semantics.

**Acceptance.** Exercise new SSL/metric initialization, ordinary/legacy resume, pseudo initialization/resume, explicit conflicts, malformed sources and recorded-model precedence. Use tiny fixtures and load/decision counters to show that the same authoritative payload reaches validation and execution without a second deserialization; genuinely different inputs and integrity checks remain distinct. Compare effective CLI/direct configurations for equivalent requests (not CLI-only presentation or confirmations). Reuse existing resume/provenance and protected-output coverage; invalid preflight must leave a pre-existing output sentinel unchanged even with overwrite. Confirm existing `run_finetune` imports/callers still work and checkpoints retain their fields and meaning.

## 5. C — Remove repeated work inside a training step

### C1. Reuse non-FIFO relational teacher targets within the step

`training/objectives.py` constructs the identical teacher distribution again at each global/local pair on the non-FIFO path. With the default six local crops and `cross` pairing that is 14 target builds for two distinct teacher slots. FIFO already builds its teacher targets once per step. Compute each used non-FIFO slot target once from the same detached, centered teacher features and temperature; retain the existing teacher logit mean subtraction, candidate order, dtype, student loss and pair reductions. Lifetime is one batch's forward/loss calculation; discard the targets even if the step is skipped. Never reuse a target across batches or state transitions. Do not route all configurations through new diagnostics or FIFO allocations just to deduplicate the code.

Compare against the per-pair reference for `cross`, `full`, legacy `same`, zero/multiple local crops and representative ordinary/weak teacher inputs. Assert target-build counts, detached targets, equivalent losses and student gradients, and unchanged center/EMA and save/resume behavior. Keep existing empty/populated FIFO and DINO controls. DINO student `log_softmax` reuse is a separate follow-up, not part of C1.

### C2. Gather selected patch tokens before the token-wise heads

`training/pretrain_loop.py` applies the iBOT heads, or the masked-feature student predictor, to all patch tokens and selects positions in the loss. These heads normalize and transform tokens independently. Gather with the same masks and row/patch order **before** the relevant heads. For masked-feature, narrow the student predictor and gather each of the four teacher block tensors before applying the pointwise final LayerNorm; then average and normalize the same selected teacher tokens. This skips unused tokenwise target work without skipping blocks or altering the teacher forward. For iBOT narrow both the student and teacher head inputs, using the same selected pre-EMA teacher logits for targets and the patch-center update. The teacher iBOT head currently runs inside the teacher-forward block before masks are sampled; move only that deterministic head call to the patch-loss block after mask generation, then gather teacher tokens with the existing mask before the teacher head. This changes program order but consumes no RNG and must not move or alter either encoder forward. Keep the full masked student and ordinary teacher encoder forwards, existing mask generation and RNG order, prefix/register handling, per-view reduction and denominator, temperature, visible-token semantics, and loss/center diagnostics. `none` and `consistency` retain their current paths. Do not move selection upstream of the backbone or use this optimization for Coordinate/Ranking point eligibility.

Assert selected head row counts and order on irregular masks and both global views; a 30% selected ratio means roughly 70% fewer *head input rows*, not a 70% reduction in step time. Compare losses, student/predictor gradients, masks and RNG, teacher center/EMA state, and applicable reporting/restore against the full-head reference. The iBOT center must still average the same selected pre-EMA logits, not centered softmax probabilities or logits recomputed after EMA. Preserve validation of masks and input alignment and require finite outputs/gradients on valid inputs; a changed GEMM shape can change rounding and may need a measured tolerance.

### C3. Batch finetune prototype assignment counts

After `optimizer.step()`, ArcFace-family diagnostic code computes similarity to the *updated* centers from the step's detached embeddings, then reads device scalars into Python for each sample. Batch the integer assignment counts (or transfer the winner indices together for host-side counting if needed on a supported backend). Preserve separate global and own-class counts, first-winner tie behavior, actual class-row order, strict target-versus-rival margin hits, and sample denominators. Keep step timing relative to `optimizer.step()` and the epoch snapshot unchanged. Never substitute the pre-update training logits. SupCon still has no prototype counts. Initially leave the second margin-head computation alone: sharing its cosine would require preserving the head's class/subcenter and margin semantics. Keep `_accumulate_loss_diagnostics` as the module-level helper; its direct-call contract is covered by `test_loss_diagnostics_counts_local_and_global_winners_differently` and `test_loss_diagnostics_margin_hits_use_margin_adjusted_target_logit`. Pretrain gradient checks are not optional logging.

Compare exact integer counts, margin totals, and epoch CSV semantics against the old path for single-/multi-center, ties, uneven batches and one-class cases, plus the SupCon no-op. Verify no per-sample device scalar readback in the new counting path and no changes to losses, gradients, optimizer updates or checkpoint content. Do not require an unsupported MPS kernel or silently enable accelerator fallback.

### C4. Reduce gradient norm device synchronizations without weakening finite checks

`_compute_grad_norm_parameters` reads one device scalar per gradient tensor into Python and runs every effective pretrain step; finetune calls the same check every usable step but uses its value only for periodic logging. The audit reports 156 gradient-bearing tensors for its ViT-tiny workload; measure the actual non-None gradient count for each acceptance recipe rather than treating that count as universal. At that reported count this can mean up to 156 host synchronizations each step. `clip_grad_norm_` then performs its own reduction in pretrain. Investigate a backend-supported batched norm/reduction and defer finetune's logging-only norm to log steps. For pretrain, retain pre-update rejection and the existing periodic `grad_norm` CSV field: the guard runs every effective step, but the numeric norm is needed only on log steps.

Use a backend-supported batched per-tensor norm plus one finite reduction (for example `torch._foreach_norm` followed by `isfinite(...).all()`) to reject NaN/Inf gradients in one synchronization. Then retain the immediately following `clip_grad_norm_(..., error_if_nonfinite=True)` as the guard for a finite-per-tensor set whose float32 global clipping norm overflows; map its failure to the existing pretraining error message. On pretrain log steps, retain the existing pre-clip norm by transferring the same per-tensor norms together and applying the existing Python-float sum of squares in parameter order; validate the logged value against the reference. A boolean finite result is not a substitute for the CSV value. Preserve the module-level `_compute_grad_norm_parameters` call seam and invoke it exactly once per effective step, branching internally for finite-only versus numeric logging work; if renamed, update `test_dino_epoch_zero_freeze_then_joint_clip`, `test_dino_ce_only_backward_reaches_backbone_projector_and_prototypes`, `test_non_finite_gradient_norm_stops_the_step`, and `test_pretrain_joint_clip_includes_no_decay_group` in the same change. Existing guard-spy, call-count, numeric-equivalence and clip-overflow tests must stay meaningful. Do not add a device float64 reduction or assume it is supported or efficient on MPS. Preserve `max_norm=3.0`, optimizer state and update order. If the batched primitive is unavailable or unsuitable on a backend, retain the current check there. Compare NaN/Inf, per-tensor overflow and global-only float32 overflow against the current path on every claimed backend. MPS microbenchmarks submitted with the third-round audit put the old per-tensor `.item()` path near 47 ms for 156 tensors, versus about 22.5 ms for batched host norm transfer on numeric/log steps and 7.7 ms for finite-only steps; this is a prioritization estimate, not acceptance evidence, and should not be read as a 156x speedup. The reported Python-float aggregation of batched values matched the per-tensor reference exactly in that environment; do not claim portable bitwise equality without reproducing the same checks. Measure synchronized versus real-step timing, actual tensor counts and step-time share. Keep existing DINO guard-spy contracts and tests.

### C5. Gate pretrain cosine similarity at its actual consumers

`cosine_similarity` currently materializes and synchronizes every step but is consumed by log-step CSV output and the progress postfix every ten steps and on the last loader step. Compute it only when either consumer needs it; keep exact values at those boundaries and leave it absent from unlogged CSV rows as before. Do not incorrectly gate it solely by `log_every_n_steps`. Check log intervals of 1, values around a postfix boundary, final steps, relational and DINO paths. DINO logs do not consume the value. Show one fewer cosine operation and scalar readback on non-consumer steps.

### C6. Batch post-optimizer finite parameter validation

When FIFO or dense objectives are active, every pretrain step calls `isfinite(...).all()` once per optimizer parameter, stacks those scalar tensors, then synchronizes the aggregate. The audit microbenchmark found this stacked implementation about 7.8 ms on its MPS workload, with parameter scans rather than synchronization accounting for most cost; a per-parameter Python `all(bool(...))` variant took about 27.8 ms and is explicitly prohibited. First measure this scan as a fraction of representative real step time. If it is below 1%, close C6 with no code change. The submitted MPS microbenchmark found approximately 7.8 ms for the current stacked implementation versus 27.8 ms for the prohibited generator form, but this isolated result is not the required real-step share measurement. Otherwise, only consider a simpler supported batched device check if it preserves the success boundary: do not update EMA/teacher heads, centers, commit the queue, or checkpoint after a nonfinite parameter update. Keep failure diagnostics and do not claim the AdamW mutation is rolled back. Validate NaN/Inf in each parameter group, finite parameters, both ordinary and dense/FIFO paths, and measure kernel/readback counts on supported CPU, MPS, and CUDA backends. If a portable foreach primitive does not support the target, retain the current implementation there. Do not reduce parameter scanning if that weakens the contract.

### C7. Reuse device-to-host loss scalars within a step

Pretrain reads scalar losses separately for progress and log consumers; finetune reads loss for its running epoch total, progress, and periodic log. Reuse one host scalar for same-step progress/log consumers where timing permits. Do not claim the per-step running loss accumulation is removable: it feeds the existing epoch average and synchronizes each usable step. Pretrain component loss values may likewise be reused across consumers. Do not force a synchronization earlier on steps that currently do not log or display a value, alter displayed precision, or change epoch accumulation. Validate progress/log rows and count tensor scalar materializations; treat this as cleanup attached to C4/C5, not an independent architecture unit.

## 6. D — Downstream command changes

### 6.1. D1 — Extract from one authoritative checkpoint snapshot

The shared-records embedding path snapshots checkpoint bytes, rereads to verify the digest, and deserializes the second read while still holding the first. The spatial checkpoint path opens the checkpoint for reconstruction, then separately reads it for the feature-contract hash and for the protected-file snapshot. Explicit embedding layer selection also constructs a model during CLI preflight and again in extraction. Representative local SSL checkpoints are roughly 163–165 MiB; removing a full read or live copy is observable work even if the operating system caches the file.

Bind model reconstruction and recorded digest to the same exact bytes. Reuse the validated model for explicit layer preflight where this avoids a second construction without duplicating a live device model or weakening protected-input drift checks. Keep a separate check for mutations at a later safety boundary when the active path requires it; a digest of bytes already in memory is not proof that the path did not change. Preserve checks before overwrite, teacher/student selection, layer/CLS validation, and existing cleanup and provenance semantics. Do not make generic snapshot replacement a prerequisite, change ONNX/external-data handling, or introduce a persistent cache. Accept using read and construction counters, peak host memory and stage timing, exact digest-to-executed-bytes checks, drift/replacement tests and invalid-layer overwrite protection. Compare existing and candidate embeddings, spatial feature contracts, and grids on the relevant checkpoint paths.

### 6.2. D2 — Separate fixed-tree monophyly from sampled partition evaluation

`cluster` builds a full output UPGMA tree from all embeddings. With labels, it also builds a separate metrics tree; when `--metrics-sample-size` caps the matched labels, it materializes the matched distance submatrix and builds a tree only to discard it and repeat both operations on the sample. Resolve the existing seeded sample in the matched manifest order first, map it to embedding row positions, and take one submatrix from the already-computed distances for one metrics linkage. Preserve full-distance normalization/scaling, full tree, full partition outputs, cutoffs, labeled cohort and sample rule. Do not refit distances, PCA or local scaling on the sample. The default distance-pair limit constrains the usual workload, so do not bundle condensed-distance storage or an approximate clustering algorithm here.

**Separate correctness change.** The current code evaluates `monophyly_proportion` on the partition metrics tree rather than the full output tree. That metrics tree is rebuilt from a labeled subset (and further subsampled when capped), so its topology need not match the corresponding tips' topology in the output tree. When capped, the current call also interprets leaf positions in the sampled linkage using unsampled IDs and labels. Aligning sampled IDs would fix that misidentification, but still measure the wrong tree. The historical reference (`ref/embeddings_tree20260206.py`, tree-level stage) computes monophyly once on the original tree before partition-metric sampling.

Compute `monophyly_proportion` once on the already-built output UPGMA topology, matching labels to tips in the output linkage's original ID order, independently of partition-metric sampling and cutoff. With partial labels, score the topology induced by the matched, labeled tips: ignore unlabeled tips, do not relink the labeled subset or assume labels for unseen tips. A represented species counts as monophyletic if its labeled tips are exactly the labeled descendants of a clade; keep the existing singleton convention. The denominator is the number of species represented by matched labels, and the score does not establish monophyly for unlabeled specimens. Without any matched labels there is no score. Keep the existing `metrics.csv` field and repeat the one value across cutoff rows when metrics are reported. Do not change bootstrap/subsample branch support, which rebuilds replicate trees from resampled embedding dimensions and has a different purpose.

Before changing monophyly implementation, add and run a characterization test against the current code that pins the known non-prefix sampled-tree/unsampled-ID misalignment and its old numeric result; only then add the corrected fixed-output-tree expectation. Test complete, partial, and absent label coverage, including a mixed clade, an unlabeled tip inside an otherwise pure clade, and a labeled singleton. Include a non-prefix sample fixture that reproduces the old silent misalignment: explicitly assert the old wrong value and the different, expected fixed-output-tree value. Also cover a rebuilt labeled tree whose topology differs from the output tree restricted to labeled tips. Assert the same monophyly value with capped and uncapped evaluation, different metric sampling seeds, and different cutoffs when the output topology and labels are held fixed. For the performance change, use a non-prefix sample and verify that all inputs to partition metrics are aligned, only one metrics linkage is built, non-monophyly metrics retain their values, and the full tree, full partition outputs, and support are unchanged. A changed monophyly value with partial labels or capped evaluation is an intentional correctness correction, not a speedup or an equivalence claim.

### 6.3. D3 — Share exact within-group distance summaries

`annotate` and `cluster` calculate the same within-group upper-triangle count, quantiles and dispersion over grouped distances. Use one implementation under `delineation` for the shared statistic, with both commands preserving their own selection, missing-label, ordering, singleton and empty-output behavior. Add a cross-command fixture asserting cluster and annotate's same-named within-group summary columns are equal, alongside each CLI's current missing/singleton behavior; existing CLI tests do not prove this shared parity. Keep corrected assignments and row/ID alignment, retain the existing report tree source and distance-loading/recomputation rules, and test with the actual outputs of `cluster`. Do not substitute Newick for linkage or add a tree cache: tie order, serialized branch precision and older products have not been qualified for interchange.

### 6.4. D4 — Keep OTU count tables compact through diversity

The OTU-table branch expands an abundance of 100,000 into 100,000 synthetic assignment rows, then counts those rows again for each threshold. Filter and compute on counts directly for the global and per-sample OTU-table path, reusing the existing alpha formulas and count-based supplied-tree MPD helper. Match header parsing, integer abundance and threshold semantics, exclusion of zero-count OTUs even at nonpositive thresholds, empty-column behavior, and missing-tip warnings and values. Do not change the tree-tip identity basis of assignment inputs, or share/filter a centroid NJ tree across different sample or threshold cohorts. Verify count-table parity against the old expanded reference on small fixtures and bounded work on a large-abundance, small-shape table.

For the assignments-plus-embeddings path, the optional NJ support annotation can reuse a copy of the already-built base tree instead of recomputing the same linkage from the same distances. Accept this separately only with preserved rooted/unrooted handling, tip IDs, edge lengths, topology, support and PD values; do not change bootstrap replicate generation or mutate the tree used for metrics.

### 6.5. D5 — Give CAM protection and execution the same image selection

The CLI selects image paths for overwrite protection; `run_cam` collects labeled rows and calls the selector again. Prepare one ordered set of paths and labels for the command invocation, use it for protection and execution, and keep direct `run_cam` calls able to prepare their own inputs. Extend existing CLI protection and CAM tests with a selector call-count assertion so output-safety and execution demonstrably share one selection. Preserve current valid-input reference resolution and selection order, `--max-images`, handling of missing images, and prediction/heatmap/filename correspondence. Verify the selection once, behavior for CSV and directory inputs, and overlay parity including original geometry and NPY modes. Keep CAM target selection, hooks, gradients and method-specific batching unchanged. Do not silently turn `--cam-batch-size` into an outer image batch or advertise `--num-workers` as newly active.

### 6.6. D6 — Prepare embedding export before destructive overwrite

Spatial export already prepares the checkpoint and layer contract before output cleanup and passes that result to execution. Embedding export still performs deterministic checkpoint/model/size checks after CLI cleanup; overwriting can therefore lose a previous output even when the new checkpoint or requested size cannot be accepted. Prepare and validate the embedding model before cleanup and reuse it in export without a second checkpoint load or model construction. Add a focused direct contract test for `_prepare_spatial_export` and reuse its CLI-level prior-publication sentinel tests; the helper currently has no direct test reference. Preserve direct-call functionality, SSL/metric/legacy source handling, register/head semantics, the requested output contract, and the existing publication/report order. Use a prior-publication sentinel test for invalid embedding inputs. Continue validating the produced ONNX graph, numerical agreement and spatial dynamic batch; do not claim that preflight protects against all failures of tracing or ORT after destructive CLI overwrite. No ONNX graph/metadata format change or validation shortcut.

## 7. E — Architecture boundaries

### E1. Dataset preflight and evaluation path identity (accepted: startup once)

Accepted on 2026-11-19: bypass evaluation preparation when metrics are disabled; otherwise prepare the configured manifest once at startup, snapshot rows, paths and labels together, and warn once and skip periodic evaluation for the invocation if preparation fails. Resume prepares a new snapshot; there is no persisted evaluation state. Keep the prepared manifest, handoff and disable-on-error state private to the invocation, out of `Parameters:`, saved args, checkpoints and CSV artifacts. Keep independent input-path ownership and overwrite checks. When training and evaluation use the same source and image root, reuse a single resolved manifest if it preserves evaluation's full ordered rows, labels, lookup rules and validation. This one-owner rule includes path resolution performed for loader-step preflight, overwrite protection, and `MultiCropDataset` construction, not just evaluator setup: count every actual resolution and reuse the exact identity-checked paths where contracts match. For an ordinary non-FIFO run, the training dataset is the third startup consumer after resume step prediction and overwrite protection; when the CSV, image root, ordered selection and validation contract match, pass the already resolved training paths through a small ordinary-run path-only handoff so `MultiCropDataset` does not call `resolve_dataset_image_paths` again. The ordinary carrier contains only ordered identity-checked paths and the minimum row identity needed to prove the match. Keep independent protected-input checks intact. Pass the prepared manifest only through the existing `_PretrainHandoff` field and `take_pretrain_handoff` pop-and-clear lifecycle. Finetune uses exactly one private path-bound handoff object, introduced with its manifest slot under A and extended with decision/payload slots under B; do not create a second private channel or duplicate manifest resolution.

### E5. Worker flags and finetune loader lifetime (accepted: document only)

Periodic training evaluation ignores the `num_workers` passed to it; the CAM option explicitly says its worker count is reserved and unused. Finetune's training `DataLoader` lacks `persistent_workers`, unlike pretrain. The operator selected no worker implementation in this effort. Potential benefit if revisited: overlap CPU image open/transform with evaluation or inference, especially on accelerator-bound runs. Costs/risks include process startup/teardown, prefetch memory, spawn behavior, deterministic error ordering, resource cleanup, and CAM gradient hooks/memory. This differs from `cam_batch_size`, which concerns a CAM method's own computation. Document the present flag scope accurately; do not activate reserved options or imply that training workers speed evaluation/CAM. Finetune `persistent_workers` is also not approved here. Keep `drop_last` changes out because of SupCon skip behavior and effective-batch/recovery identity.

### E6. Resume preflight cost and baseline test status

`_pretrain_loader_steps` is evaluated for every resume, whether or not dense is enabled. With a CSV it needs only the selected row count, but currently resolves image paths first, causing per-row `exists` checks and possibly a recursive directory index; that resolution also preserves ambiguous-reference errors. The existing resume contract requires readable training data. Preserve full preflight resolution (including ambiguity errors), dense `steps_per_epoch` and the zero-step guard unless reuse or a cheaper path can demonstrate the same validation and failure timing for dense and non-dense resume.
